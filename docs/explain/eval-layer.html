1 · Why this exists

An "eval" is a check that says whether the system did its job. For laiive the job is one question: what can I do tonight? A good answer finds real gigs, in the right place and time, in the user's language.

Three earlier docs each covered one build step. Eval phases 0–1 explained how answers and thumbs get saved. Eval phase 2 wired the first twelve test cases. Evals and monitoring compared the retriever with the pusher. This doc does not repeat them. It shows the whole layer as it stands on 2026-10-09: what is captured, what is tested, what real users said, and where the gaps are.

Two things changed since those docs. First, the offline suites grew from 12 cases to 56, and all of them pass. Second, on 2026-10-09 we read real-user feedback as a whole for the first time. Before that, a thumbs-down was a row nobody looked at. Now it lands in a named "thread" (a recurring line of failure) with a count that can be followed week to week.

The first read gave a clear answer. The main problem is not wrong answers. It is empty answers: about 55% of the turns worth reading found no events.

Key takeaways

  • Production writes three tables joined by one request_id; a script now reads them as threads.
  • 56 written cases run in pytest; all green. A weekly job runs the ones that need a model.
  • The biggest real-user line is "no events found", not "wrong answer".
  • Prior docs are linked, not repeated. Recommendations they made that are now done are flipped to green in place.

3.4 · Decisions, and why

  • ①One key, born in the gateway. The gateway mints request.id (server.ts:22) and every service adopts it (request_id_from). Rejected: a key per service, which made rows unjoinable. Cost: the join only works for services that read the header; both chat services do now.
  • ②90 days, except thumbs-down. A thumbs-down turn is the most useful row we have, so it is never pruned. Ups are pruned with everything else. Cost: kept rows grow forever; at human click volume that is a few rows a month (accepted in evals and monitoring rec. 7). pg_cron (a scheduler inside Postgres) so no service has to be running for the prune to happen.

3.5 · For a scalable system

The ceiling is the one-thread-per-turn write (marked ponytail: in the code). A burst spawns a thread per turn, and a thread mid-write dies on shutdown. Upgrade: a bounded queue and a single writer. Not needed at nine users.

3.6 · Security

All three tables have row-level security on and no policies, so only the service-role key can read them. The gateway and the retriever hold that key. conversation_logs.payload holds the full message history the client sent, so it is personal data; the 90-day prune is its main protection.

Key takeaways — capture

  • Question in conversation_logs, answer in eval_records, label in turn_feedback; join on request_id.
  • Answers exist only from 2026-08-26. Older answers are recovered from the next turn's history (§6).
  • A failed write is counted on /health, not hidden.

4 · Tracing: Phoenix, local only LIVE

A trace is a timed tree of one turn: the turn, then each stage, then each OpenAI call inside a stage. laiive sends traces to Arize Phoenix, an open-source trace viewer, through OpenTelemetry (OTel, the standard format for traces).

services/shared/laiive_shared/tracing.py:48–83 — off unless asked for ③LIVE
def setup_tracing(service: str, *, enabled: bool, endpoint: str, api_key: str = "") -> bool:
    if not enabled:
        return False
    try:
        from phoenix.otel import register
        register(project_name=f"laiive-{service}", endpoint=_with_otlp_path(endpoint),
                 batch=True, auto_instrument=True, ...)
    except Exception as e:
        logger.warning("Phoenix tracing off (%s): %s", type(e).__name__, e)
        return False

The retriever opens one turn span per request (pipeline.py:116) carrying laiive.request_id, so a trace can be matched to its Supabase rows. Stages are children: moderate, classify, route, execute, compose (pipeline.py:168–264).

4.1 · Decisions, and why

  • ③Production has no PHOENIX_* secrets, so tracing is off there. It runs only on a laptop: make phoenix (Makefile:23) starts the container, UI on port 6006. The owner decided on 2026-10-09 to keep it that way: no Phoenix Cloud. Why: the budget is $30–50 a month, and the feedback read needs only Supabase. What it costs: when a production turn goes wrong, there is no trace of it. The eval_records row (cyphers, errors, latency) is the only record. The old LANGFUSE_* secrets on Fly are left over from the previous tracer; the owner is removing them.

Key takeaways — tracing

  • Code is ready; production does not use it, by choice.
  • For a production failure, read eval_records; reproduce locally with Phoenix on.
  • DEPLOY.md:48–49 still lists PHOENIX_* as service secrets (rec. 3).

5.3 · Decisions, and why

  • ⑧Always-true rules are code, not prompt words. A first message cannot be a "refinement"; "near me" without a location must ask where. Putting the first rule in the prompt flipped another case ("actually, what about Lisbon?") the wrong way. Code cannot drift. Cost: two places hold classifier behaviour.
  • ⑨Run the query, don't regex it. Regex over generated Cypher (the graph query language) went red on harmless rewording and green on a query that returned nothing. Running it on a frozen 18-event graph found two real bugs on its first run (README, 2026-09-23). Cost: needs a Neo4j container, so it is weekly, not on every push.
  • ⑩Weekly, allowed to fail. Model answers vary, so a red run means "go read", not "broken build" (continue-on-error). Rejected: nightly, which would be noise at this traffic. The workflow reached main only with v0.7.0, and GitHub runs schedules from the default branch, so it has never run. First run expected Monday 2026-10-12.
  • ⑪No model grader. Every check above is a rule. "1–3 short sentences" or "answer in Italian" does not need a model to judge, and a rule has no bad days. A model grader is deferred to where only it can judge (tone), and it must first be calibrated against the owner's own labels.

5.4 · For a scalable system

Each live case runs once. A model can pass a case today and fail it tomorrow with the same prompt; one run cannot tell those apart. The README records manual re-runs ("Three runs green", README.md:153) but nothing computes a rate. The frozen graph has no bad geocodes or duplicate venues, which the real graph does: green here means the code is right, not that production answers well.

Key takeaways — the suites

  • 56 cases, all code-graded, all green.
  • Each dataset carries a prompt_version; a prompt bump without re-reading the cases fails a test.
  • The weekly job is the only thing that runs the model tier, and it has not run yet.
  • None of the 56 cases came from a real user complaint.

6 · Real-user feedback, read as threads LIVE

6.1 · Goal

Turn a pile of thumbs and failures into a short list of lines to fix. The owner asked for "threads, so I see the main lines, not single logs" (plan step 2, docs/plans/real-user-feedback.md). Run it from services/retriever: uv run --no-sync python -m agent.scripts.feedback [--days 7] [--no-save].

6.3 · How the data moves and transforms

services/retriever/agent/scripts/feedback.py:101–112 — recovering answers from before captureLIVE
def replied(messages: list[dict]) -> str | None:
    """The answer as the next turn of the same chat resent it in its history.
    Answers were captured only from 2026-08-26, and most thumbs are older.
    ponytail: O(n^2) over chat turns; index by first message if it grows."""
    n = len(messages)
    for _, later in chats:
        if len(later) > n and later[:n] == messages:
            if later[n].get("role") == "assistant":
                return later[n].get("content")
    return None

The client is stateless: each request resends the whole chat. So turn N+1's payload contains turn N's answer. If a later turn exists, the old answer is recovered. If the user never sent another message, it stays answer-not-recorded.

6.5 · Decisions, and why

  • ④Hard facts are labelled in code. "The graph was down" or "HTTP 429" is a fact in the row; asking a model would add cost and a chance to be wrong. The model only does what code cannot: read the question and guess the cause.
  • ⑤One model call for the whole batch. All picked turns go in one request (composer model, about 2 cents, temperature 0, JSON output), with the saved thread names as a menu to reuse. Rejected: one call per turn, which costs more and cannot see that two turns share a cause. Cost: the batch must fit in one context window; at 87 turns it is far from the limit. Anything the model skips lands in unsorted, so no turn disappears silently.
  • ⑥Split big failure threads by cause. "No events" covered over half the turns, which is a symptom, not a fix. A thread at or above max(6, turns/4) gets a second call that splits it into parent/child. Cost: one extra call per big thread.
  • ⑦Save names and counts, never user text. failure_modes.json is committed, so it must hold nothing a user typed. The saved names come back next run, so a thread can be followed week to week ("+3 vs last run"). Known ceiling, from the plan: names drift between runs; step 3 (owner reads and prunes) settles them.

6.6 · For a scalable system

replied() compares every turn with every other: O(n²), marked ponytail:, fine at 328 turns. _get pages 1000 rows at a time with no upper bound; with --days unset it reads all history. Both are fine for a weekly read of hundreds of rows.

6.7 · Security

  • The script uses the service-role key and only sends GET requests. It cannot write to Supabase.
  • User questions, answers and reasons are sent to OpenAI for grouping. That is the same provider that already processed them during the turn, so no new party sees them. The module docstring says "user text never leaves this terminal" (feedback.py:10), which is not quite true (rec. 6).
  • User text is hostile input inside the grouping prompt: a reason could say "ignore your rules". The worst outcome is a wrong thread label in a local report. Accepted for a grouping script; not acceptable once a model grader scores answers (carried from phases 0–1 rec. 6).
  • Thread descriptions are written by the model and committed. The prompt tells it never to quote a user; nothing enforces it. The first run's descriptions are general (checked by reading the file).

Key takeaways — the feedback read

  • 87 turns became 10 named threads in one run, for about 2 cents.
  • Empty results dominate: ~55% of turns read.
  • The loop is open: a thread does not yet become a test case (plan step 4).

7 · Against Anthropic's eval guide

Anthropic's article "Demystifying evals for AI agents" lists practices for testing AI systems. Here is how laiive stands against each. "pass@k" means "at least one of k tries passed"; "pass^k" means "all k tries passed". For a user-facing chat, pass^k is the one that matters: the user gets one try.

8.2 · Recommendations

  1. Close the loop first: turn the top threads into cases (plan step 4). Start with no-events-found/no-events-near-me and missing-events: both can be retrieval cases on the frozen graph, so they run on every push for free. Each case names its request_id, so a fix is proven against the real complaint.
  2. Fix the stale eval README and weekly summary before Monday's first run. evals/README.md:18, :121 and :132–134 still describe expected_patterns as an xfailed regex; it was removed in corpus v3.0 (test_eval_cases.py:18). evals-weekly.yml:94–98 tells the reader about "seven known_gap cases"; grep finds none left in the datasets. The README's "Next" section (:238) also still calls execute-and-compare future work. A first weekly summary that describes things that no longer exist will teach the reader to skip it.
  3. Mark the PHOENIX_* rows in DEPLOY.md:48–49 as local only. They list Phoenix secrets for the retriever and pusher, but production has none, by the 2026-10-09 decision. Someone following the runbook would set them up, or think they are missing.
  4. Watch the first weekly run on 2026-10-12. Check that the OPENAI_API_KEY repo secret exists (the job fails loudly if not), that the Neo4j service starts, and that the summary is readable. If it does not appear, trigger it by hand (workflow_dispatch).
  5. Measure pass^k cheaply: run the model tier three times in the weekly job. A shell loop around the existing pytest call, no new dependency. Report a case as stable only if it passed all three. Cost: about 3× a run that already costs cents. Owner's call.
  6. Correct the feedback.py docstring (line 10). It says user text "never leaves this terminal"; it goes to OpenAI for grouping. Say so: "user text goes to OpenAI for grouping, the same provider as the chat, and nowhere else". One line.
  7. Rename city-named threads in step 3. no-events-in-bergamo and no-events-in-torino are places, not causes; the split prompt itself says "never a city name on its own". A cause would be "no coverage for a place we were asked about". The saved names steer next week's run, so fix them by hand once.
  8. When the model grader comes, fence user text in its prompt and calibrate it against the owner's step-3 labels before trusting a number from it. Carried from phases 0–1 rec. 6.
  9. Still open from earlier docs: moderate() fails open with only a log line (phase 2 rec. 4), and the gateway's two telemetry inserts still only log on failure (logging.ts:54, feedback.ts:45), while the Python writers now count failures on /health.
  10. Accepted, because — production tracing stays off. The budget is fixed, and eval_records holds the cyphers, errors and timings of every turn. Revisit only if a production failure cannot be reproduced locally.

Key takeaways — what to do next

  • Rec. 1 is the one that changes quality: real complaints become cases.
  • Recs. 2–4 are small and time-bound: do them before Monday 2026-10-12.
  • Recs. 5 and 8 are the next eval capabilities, in that order.
