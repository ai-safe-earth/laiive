1 · Why this exists

The programme file opens its evals section with one sentence: “Nothing after this is a claim without it.” (docs/roadmap/01-program.md §3). Two earlier documents — eval phases 0–1 and eval phase 2 — each described one build step for the retriever. Neither answered the question this one does: across the two conversational services, what can actually be measured today, and what happens silently?

The answer is lopsided in a way that is invisible from any single file. The retriever has a complete loop: every turn writes an answer-side record, a thumbs-down attaches a label to it, a nightly job prunes everything unlabelled after 90 days, and twelve hand-labelled cases run in pytest with a tripwire that fires when the prompt they describe changes. The pusher — the service that writes to the graph, the only one whose mistakes are durable — has none of it. Its 52-case dedup corpus has never been reviewed, so nothing is wired to it; its chat turns produce no answer-side row; its three OpenAI clients are untraced; and it throws away the correlation id the gateway hands it, which means even the request-side rows the gateway does write for it cannot be joined to anything the pusher logged.

Before this document, the honest summary of “how are we doing on evals?” was a shrug per service. What was impossible was the comparison: knowing that a bad answer is recoverable from production data within a week, and a bad write is not recoverable at all.

Key takeaways

  • The retriever is instrumented end to end; the pusher is dark.
  • The asymmetry is backwards from risk: the dark service is the one that writes.
  • This doc is a state-of-play reading of the working tree at 7492a33, not a build step — nothing here was implemented for it.

3 · Retriever at runtime — capture, label, prune RET

3.1 · Goal

Make every production turn recoverable later, at a cost that can never break the turn itself. That splits into three obligations that pull against each other: the record must contain enough to judge the answer (the question, the generated Cypher, the cards, the final text, the errors and the latency); it must be written on a path where a failure is invisible to the user; and it must not accumulate personal text forever. The shape below is what satisfies all three — a fire-and-forget write from two services that share a key, plus a nightly prune that spares anything a human complained about.

3.2 · Data flow

Fig. 2 — One turn, and the three rows it can produce. The feedback exchange is optional and arrives seconds to minutes later; everything above it is unconditional. The retry/failure branches inside the pipeline are omitted — they surface here only as the errors array on the record.

3.3 · How the data moves and transforms

The id is minted and sanitised at the boundary. Every proxied request has the client's own x-request-id deleted before a trusted one is written in its place — the same list that protects x-user-id and x-internal-key.

def _request_id(raw: Request) -> str:

The write leaves the request path entirely. In the SSE generator the finally: block runs before the done frame is yielded, so anything blocking there delays the last frame the user waits for.

services/retriever/agent/api.py:73–87 — off the hot path, with its ceiling written downRET
def _write_eval_record(request_id: str, result: TurnResult, start: float) -> None:
    """Fire-and-forget on a daemon thread: in the SSE path the finally: runs
    before the done frame is yielded, so a blocking POST there would delay it.

    ponytail: one unbounded thread per turn, fine at current volume and wrong
    under load - a burst spawns a thread each, and a daemon thread mid-POST
    dies silently on shutdown, losing that record. Upgrade path when turns/sec
    justifies it: a bounded queue plus a single writer thread, dropping oldest
    on overflow so the corpus degrades instead of the turn.       // ③
    """
    threading.Thread(
        target=eval_records.write,
        args=(request_id, result, int((time.perf_counter() - start) * 1000)),
        daemon=True,
    ).start()

3.4 · Decisions, and why

  • ①The gateway owns the id, and deletes the client's. The alternative — trusting a client-supplied correlation id — is cheaper and would let a caller write telemetry rows that impersonate somebody else's turn. Cost: a direct call to :8002 (tests, curl) gets a locally minted id that joins to nothing, which is the correct degradation.
  • ②Request side and answer side are written by different services, into different tables. The obvious design is one row written once. It was rejected because the response streams: the gateway proxies bytes it never buffers, so it cannot see the final text, and the retriever cannot see the client-sent history that the gateway parsed. Cost: a turn can produce a half-pair — an eval_records row with no conversation_logs partner if the gateway's fire-and-forget POST fails. Every query in queries.sql uses left join for exactly that reason.
  • ③A daemon thread per turn, not an await and not a queue. Awaiting the POST inside finally: would add a Supabase round trip before the done frame — directly visible latency on the one frame the user is waiting for. A bounded queue with a single writer is the right shape and is written down as the upgrade path; it was not built because at current volume it is machinery with no symptom. The known ceiling is real and named in the code: a burst spawns a thread each, and a thread mid-POST at shutdown loses its record silently.
  • ④Telemetry failures are swallowed, loudly in the log and invisibly to the user. The rule is that a turn must never break because a record write did. Cost: a broken SUPABASE_SERVICE_ROLE_KEY degrades the corpus to nothing while every turn stays green, and the only evidence is logger.error lines nobody is watching. There is no counter and no alert on this path.
  • ⑤The down is the event; the up is an inert label. A thumbs-down posts immediately with a null reason, because the click itself is the information and asking for a reason first loses most of them. An optional typed reason arrives as a second row for the same request_id, which is why query 1 groups and takes max(reason). Ups are stored but pin nothing in retention — engagement-scale exemptions would hollow out the TTL.

3.5 · For a scalable system

The ceilings here are all volume-linear and all known:

  • Thread per turn (③). Fine at hand-triggered volume. At sustained traffic the first symptom is thread-count pressure in the retriever pod, not lost data; lost data comes second, at shutdown. Upgrade path is in the docstring.
  • Table growth is append-only and bounded by the 90-day prune, with eval_records_created_idx and conversation_logs_created_idx existing precisely so the age scan is cheap. What is not bounded is the labelled subset: every down-rated turn is kept indefinitely, by design, and that set grows monotonically forever. At human-complaint scale this is nothing; it is worth revisiting only if downs ever become automated.
  • payload jsonb holds the entire client-carried history, so a row's size grows with conversation length. A long conversation writes its whole prefix again on every turn — quadratic in storage per conversation. Acceptable because conversations are short and the prune is aggressive; it would not survive a product change to long-lived threads.
  • The weekly read is a human. Phase 3 is deliberately manual, and its ceiling is attention, not compute. Query 4 exists so that ten minutes can be spent deciding whether to spend the other ten.

3.6 · Security

  • Three services hold the master service-role key (gateway, retriever, search). Each needs INSERT on one or two tables and SELECT on none. Compromise of any one is compromise of the whole database — the mitigation is a scoped insert-only Postgres role, and it has not been done.
  • The telemetry tables are RLS-on with zero policies, so a leaked anon key reads nothing. There is no client read path to any of the three.
  • The corpus is attacker-influenceable by construction. final_text derives from user-shaped conversations, payload is the user's text, and reason is hostile free text stored raw — correct at write time, but every future reader is a target. When the phase-4 judges interpolate these columns into prompts, they must be fenced as data from the first prompt, not after an incident.
  • An anonymous unauthenticated endpoint writes with the service role (/api/chat/feedback). It is safe only because the handler constructs the row from three validated values; any column added to that insert must preserve the property that the client cannot name a column.
  • Personal data lives in two of the three tables and is joined by request_id. Any deletion request has to sweep conversation_logs, eval_records and turn_feedback together; there is no such procedure today.

Key takeaways — runtime

  • One id, minted at the gateway, carried by the retriever, joins three tables.
  • Every telemetry write is fire-and-forget and cannot fail a turn — which also means a broken key is silent.
  • Retention is in the database (pg_cron), spares thumbed-down turns, and needs no running service.

4 · Retriever offline — twelve cases with a tripwire RET

4.1 · Goal

There is still no eval harness: python -m evals.run is phase 4 and does not exist. What exists is twelve hand-labelled cases that run, loaded by pytest, split into a tier CI can hold and a tier that needs an OpenAI key. The point of phase 2 was not to move a quality number — it moved none — but to stop the corpus drifting silently away from the code it describes, which is what had already happened to it for five months.

4.2 · Data flow

4.4 · Decisions, and why

  • ⓐThe corpus tests itself before it tests the code. Two tests assert case counts and claimed checks. This looks like tautology and is not: the set spent months quarantined precisely because its labels named a taxonomy no function produced, and pytest reports an unclaimed parametrization as nothing at all. Cost: the counts (7 and 5) are hard-coded, so adding a case means editing a test — deliberate friction.
  • ⓑVersion pin over prose. The rejected alternative was a sentence in the README saying which prompt the cases describe, which is what existed and what failed. Cost: a legitimate prompt reword now goes red until someone re-reads five cases. That is the feature.
  • ⓒshould_not_contain is asserted in both tiers, in two different readings. Offline it is the durable property (a generated mutation is refused before execution, true of every prompt revision, costs no tokens); online it is the literal one (the generator did not emit one). The alternative — asserting it only where a model is available — would put the corpus's real gate behind an API key.
  • ⓓThe integration tier depends on OpenAI but deliberately not on Neo4j. The Cypher cases assert on what the model emits against a static schema string, so the Aura free instance auto-pausing cannot turn a model regression into a red build. Cost: the static schema drifts from the real one, and nothing checks that it hasn't.

4.5 · Security

One thing here is a live safety edge rather than a test concern. detect_injection's DROP rule is \bDROP\s+(CONSTRAINT|INDEX|DATABASE)\b (safety_guard.py:98), and the corpus's own sf_004 — 1' OR '1'='1; DROP TABLE events-- — slips it; the bare DROP rule in validate_read_only (safety_guard.py:65) is what actually stops it. That is fine while detect_injection is only ever a signal, and stops being fine the moment it is used as a pre-flight gate on user text. Separately, moderate() fails open on any exception with nothing louder than a logger.warning (safety_guard.py:116–126), so a bad key degrades the moderation layer to a no-op silently — the availability trade is right for a consumer chat, the silence is not.

Key takeaways — offline

  • Twelve cases run; there is still no harness, and evals/ holds no code.
  • The corpus is pinned to the prompt version, so the drift that quarantined it cannot recur silently.
  • The integration tier — 11 live assertions — is scheduled nowhere and runs only when typed.

5 · Pusher — fifty-two cases and no instruments PUSH

5.1 · Goal

Everything above describes a service whose mistakes are ephemeral: a bad answer is a bad answer, the user asks again. The pusher's mistakes are durable — they are rows in the graph that every future retriever turn will read. The measurement story for it should therefore be stronger than the retriever's. It is instead empty, and the emptiness has three distinct causes, which is why it has never been fixed by accident.

5.2 · Data flow

Fig. 3 — The same turn shape as Fig. 2, with the two breaks marked. The graph write itself (/validate-event → neo4j_writer) is omitted: it is the step whose outcome nobody records, which is exactly why it cannot be drawn as an arrow into any table.

5.4 · Decisions, and why

  • ⑥Minting locally was never decided — it is the original code, and the retriever moved. Phase 0 changed the retriever to adopt the gateway's id specifically so the two halves would share a key; the pusher simply was not in that change's scope. Cost today: conversation_logs rows for /api/push/chat and /api/publish exist and are unjoinable to any pusher-side log line, so the one table that does hold pusher data is half-useful. The fix is the same five lines the retriever has, plus threading Request into the handler.
  • ⑦No answer-side record, because nobody specified what the answer is. For the retriever the unit is obvious (final text, cards, Cypher). For the pusher the interesting unit is not the assistant's sentence — it is the write verdict: what draft was extracted, did the writer MERGE or 409, was a near-duplicate created, did the walk advance. That needs a schema decision, which is why it has not happened by default. Cost: the failure mode the dedup corpus was born from — silent duplicates — is by construction invisible in production. We know it happens because someone watched it happen once.
  • ⑧Three bare clients instead of the shared factory. The roadmap already books this: phase 4 (multi-provider routing) moves every module-level client onto laiive_shared/llm.py, and the pusher's three are named in that plan along with the conftest patch list that must move with them. Until then, tracing the pusher means enabling nothing — the flag has no effect there. Cost of waiting: a pusher extraction regression has no trace to read, only a mocked test suite that will keep passing.

5.5 · For a scalable system

The pusher's ceiling is not throughput, it is auditability of writes. Every sweep, every publish and every walk step mutates a shared graph that the retriever reads and that has no undo. At current volume a human can eyeball a dry-run report; the moment writes are scheduled (flows/serve.py is not running, so nothing fires today) the number of unreviewed writes per week stops being eyeball-sized, and there is no table to read instead. The order that matters: the write-outcome record must exist before the scheduler does, not after.

5.6 · Security

The pusher is the only service here that does not hold the Supabase service-role key — a direct consequence of writing no telemetry, and a genuine (if accidental) reduction in blast radius. It holds the Neo4j credentials instead, and is protected from direct traffic by INTERNAL_API_KEY (install_internal_auth, api.py:55), which makes 8003 return 403 to anything not carrying the gateway's key. The security cost of ⑦ is not exposure but forensics: if a bad actor or a bad prompt writes junk into the graph, the only record of how it got there is the request-side payload in conversation_logs under an id that matches nothing in the pusher's own logs.

Key takeaways — pusher

  • Three independent gaps: the discarded id, the missing answer-side record, the untraced clients.
  • “21 of 52 silently duplicate” is a hand-verification, not a measurement — nothing would catch a regression.
  • The service with irreversible side effects is the one with no write-outcome telemetry.

6 · The join: one key, three tables, and where it stops

The unifying mechanism is request_id, and the thing built to be enabled by it is not a dashboard — it is a five-minute habit. evals/queries.sql is a file of five queries to paste into the Supabase SQL editor, written so that error analysis (phase 3) starts as a Monday reading rather than a project. The argument for it is in the phase-2 doc: a corpus nobody reads is just storage cost.

services/retriever/evals/queries.sql:33–52 — query 1, the complaint queueRET
select f.created_at,
       max(f.reason)                        as reason,       -- a reason arrives as a 2nd row
       c.payload -> 'messages'              as conversation,
       e.query_type, e.moment, e.final_text, e.row_count,
       e.cyphers, e.errors, e.latency_ms,
       c.duration_ms - e.latency_ms         as edge_overhead_ms
from turn_feedback f
join eval_records e using (request_id)
left join conversation_logs c on c.request_id = f.request_id
where f.rating = 'down'
group by f.request_id, ...
order by f.created_at desc limit 100;

Two of the five are the ones worth knowing about, because they need no labels at all. Query 2 is “failures nobody complained about” — array_length(e.errors, 1) > 0 with no feedback row — on the reasoning that thumbs are a biased sample of failure and the unbiased half is the users who simply left. Query 3 is “empty-handed turns”: no error, no cards, which for a discovery product is usually a supply problem and reads as a shopping list for the next sweep. Query 4 is one row per week and exists so that ten minutes can decide whether to spend the other ten:

services/retriever/evals/queries.sql:99–110 — query 4, the weekly pulseRET
select date_trunc('week', e.created_at)                             as week,
       count(*)                                                     as turns,
       count(*) filter (where array_length(e.errors, 1) > 0)        as error_turns,
       count(*) filter (where coalesce(e.row_count, 0) = 0)         as empty_turns,
       count(distinct f.request_id) filter (where f.rating = 'down') as downs,
       count(distinct f.request_id) filter (where f.rating = 'up')   as ups,
       percentile_disc(0.5)  within group (order by e.latency_ms)    as p50_ms,
       percentile_disc(0.95) within group (order by e.latency_ms)    as p95_ms
from eval_records e
left join turn_feedback f on f.request_id = e.request_id
group by 1 order by 1 desc;

Now the boundary. Every one of these five queries starts from eval_records or turn_feedback. Both are retriever-only tables. Run any of them and the pusher does not appear — not as a zero, not as a gap, simply not at all. The equivalent pusher questions have no query, because they have no table:

questionretrieverpusher
How many turns last week?query 4count conversation_logs by route — request side only
Which turns errored?query 2, from errors[]not recorded; status in conversation_logs is the HTTP code, and the SSE path returns 200 with an error frame
Which turns produced nothing useful?query 3, from row_countno equivalent — “extracted a draft” is not recorded
Which turns did a human complain about?query 1, from turn_feedbackno feedback control on the publish chat
p50 / p95 latencyquery 4, from latency_mspartial — conversation_logs.duration_ms exists
Did this write duplicate an existing event?n/athe central question, recorded nowhere

One more instrument is worth naming because it is misleading: the retriever exposes /metrics, and it returns a constant.

services/retriever/agent/api.py:498–504 — an endpoint named for something it does not doRET
@app.get("/metrics")
def get_metrics():
    """Simple metrics endpoint. For detailed observability, use Langfuse."""
    return {
        "status": "operational",
        "langfuse_enabled": settings.langfuse_enabled,

It is not proxied by the gateway, so nothing can reach it from outside; and with LANGFUSE_ENABLED defaulting to false the note points at an empty dashboard. Real monitoring of the process lives elsewhere and is genuinely well-built — the shared /livez+/readyz split with a readiness cache that keeps successes for 20 seconds but never caches a failure, so a recovered dependency is picked up on the next probe (services/shared/laiive_shared/health.py:33–59).

Key takeaways — the join

  • request_id is the whole mechanism, and it stops at the retriever.
  • Five queries make phase 3 a habit; all five are blind to the pusher.
  • Process health (livez/readyz) is solid across both services; work health is not.

Discovered while writing this, in the order I would do them. Items 1–3 are all small; item 4 is the one that changes what can be known.

  1. The pusher did not adopt the gateway's x-request-id — done since this document. services/pusher/agent/api.py:241 now calls the shared request_id_from(raw), the same contract as the retriever. Verified 2026-10-09; see eval-layer.html §3. Original note: five lines, copied from services/retriever/agent/api.py:66–70, plus taking raw: Request in chat_stream. It costs nothing, it is independent of every other item here, and until it lands the conversation_logs rows already being written for /api/push/chat and /api/publish cannot be correlated with a single pusher log line. Do this first because everything else on the pusher side assumes it.
  2. GET /metrics in the retriever — deleted since this document. A comment at services/retriever/agent/api.py:435 records why it went and points at eval_records and Phoenix instead. An endpoint that lies about having metrics is worse than no endpoint — when real metrics arrive, this name will be wanted and will be occupied. One-line-ish deletion, no caller anywhere in the tree.
  3. The evals/__init__.py docstring — fixed since this document. It now says "datasets only, no framework". Verified 2026-10-09. Carried over unresolved from the phase-2 doc's recommendation 5; noting it again because it is still true and still one line.
  4. The pusher's answer-side record — decided and built since this document. The service-role key is now in the pusher, as this item warned. Verified 2026-10-09. Original note: This is the real gap (⑦) and it is a schema question, not a coding one.   6. That is the right availability trade and the wrong observability one: a rotated key silently empties the corpus while every dashboard stays green. The lazy version is a module-level integer exposed on the deep /health, not a metrics stack.
  7. Accepted, because — the 90-day prune keeps labelled turns forever. The down-rated subset grows monotonically with no ceiling. At human-complaint volume this is a handful of rows a month and adding a second TTL for it would be machinery with no symptom. Key takeaways — what to do next

  • Item 1 (adopt the gateway id in the pusher) is five lines and unblocks every pusher-side measurement that follows.
  • Item 4 is the decision, not the code: name the pusher's write verdict, and the dedup corpus becomes measurable in production instead of by hand.
  • Items 2 and 3 are deletions and a docstring — do them the next time either file is open.
  • Nothing here blocks on the dedup review; the review blocks phase 4, not the instruments.
