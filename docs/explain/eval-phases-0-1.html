1 · Why these phases exist

The roadmap's rule is evals before optimisation: accuracy, cost and voice work are all claims until a harness can tell whether a change helped. The eval audit of 2026-08-26 found the system could not even begin, for two concrete reasons:

  • Answers were never stored. The gateway's conversation_logs captured the request side only — 123 turns, zero labelable outputs. You cannot label, grade, or regress-test an answer that no longer exists once the SSE stream closes.
  • The two halves could not be joined. The gateway injected x-request-id into every proxied request (services/gateway/src/proxy.ts:23), but the retriever ignored it and minted its own uuid4(). Even if answers had been stored, no key connected an answer to its request.

The audit also corrected the build order. Roadmap §3 wanted the harness and judge rubric first; the corrected sequence is capture → cheap label → wire existing cases → error analysis → judges — you need a corpus before a rubric means anything. Phase 0 is the capture. Phase 1 is the cheap label: a thumbs-down from the person who just read the answer, the one signal that costs nothing to produce and compounds while everything else is built.

Key takeaways

  • Phase 0 fixes a plumbing gap (shared key + stored answer), not an eval-quality gap. It makes every later phase possible.
  • Phase 1 was deliberately scheduled early because it depends on nothing and its value is cumulative — every day without it is labels lost forever.
  • Both phases are pure telemetry: no user-visible behaviour of chat changed, except one small button.

2 · The system, and where the phases land

laiive is four services behind one published surface. The SPA talks only to the gateway (:8000); the gateway authenticates, rate-limits and proxies to the Python services, which trust its identity headers because they are otherwise unreachable (X-Internal-Key). The retriever answers chat turns by reading the Neo4j graph through a classify → route → execute → compose pipeline and streaming real tokens back as named-event SSE. Chat is stateless: the client resends the full history each turn.

Fig. 1 — Where the phases land. ①–③ are decisions explained in §3. Pusher (:8003) and search (:8004) are untouched by these phases and omitted.

Both phases are deliberately additive at the edges: phase 0 lives in the retriever's turn-finalisation path and a new table; phase 1 lives in one React component, one native gateway route, and a second table. The pipeline, the protocol, and the proxy behaviour for chat are unchanged.

Key takeaways

  • The gateway was already the single place every request passes through — the eval design leans on that instead of adding a collector service.
  • Supabase Postgres was already in the stack for auth and conversation_logs; both new tables reuse it. No new infrastructure was introduced for evals.
  • Each new table sits at the trust boundary nearest the data it records: the answer is written by the service that produced it, the label by the surface that received it.

3 · Phase 0 — capture the answer P0

3.1 · Goal

Give every chat turn a durable, joinable record of what the system answered and how it got there: final text, the cards shown, the Cypher that ran, the classification, latency and errors — keyed by the same x-request-id the gateway already logs the request under. After this phase, a production turn is an eval candidate by default.

3.3 · How the data moves and transforms

The join key is born at the gateway. Fastify assigns request.id; the proxy strips every client-sent copy of the headers it asserts, then injects its own — so by the time the retriever sees x-request-id, it is trustworthy:

The retriever previously minted uuid4() here — the audit's un-joinable halves. Now both chat endpoints adopt the inbound header, falling back to a local uuid only for direct calls (tests, curl against :8002):

services/retriever/agent/api.py:64–68 — adopt, don't mintP0
def _request_id(raw: Request) -> str:
    """The gateway's id, so the record joins conversation_logs; the gateway
    strips client-sent copies, so the header is trustworthy. Minted locally
    only for direct calls (tests, curl against 8002)."""
    return raw.headers.get("x-request-id") or str(uuid.uuid4())

The capture point is the stream generator's finally:. The pipeline already accumulates everything about the turn into a TurnResult as it streams — so when the generator winds down (success, error, or client disconnect), the full answer is sitting in one object and no extra bookkeeping was added to the hot path:

services/retriever/agent/api.py:405–439 — _generate: stream, then captureP0
def _generate(request_id, user_message, history, location, timezone=None):
    # Deliberately a *sync* generator: run_turn blocks (OpenAI + Neo4j), and an
    # async generator would hold the event loop between yields — no streaming.
    # Starlette runs sync iterators in a threadpool.
    result = TurnResult()
    start = time.perf_counter()
    try:
        for payload in get_pipeline().run_turn(
            user_message, history, location, result=result, timezone=timezone
        ):
            yield sse_frame(payload)
    except Exception as e:
        logger.opt(exception=True).error("[{}] SSE stream error: {}", request_id, e)
        yield sse_frame(Error(code="internal_error", message="Something went wrong."))
    finally:
        log_turn(request_id, user_message, ...)
        _write_eval_record(request_id, result, start)   # ③ non-blocking
    yield sse_frame(Done(request_id=request_id))        # after finally — must not wait
services/retriever/agent/api.py:71–78 — off the yield pathP0
def _write_eval_record(request_id: str, result: TurnResult, start: float) -> None:
    """Fire-and-forget on a daemon thread: in the SSE path the finally: runs
    before the done frame is yielded, so a blocking POST there would delay it."""
    threading.Thread(
        target=eval_records.write,
        args=(request_id, result, int((time.perf_counter() - start) * 1000)),
        daemon=True,
    ).start()

The writer flattens the in-memory TurnResult (Pydantic objects, card models, classification) into one flat row — the transformation from live pipeline state to eval corpus:

Note what is not stored here: the user's message and history. Those already live in conversation_logs.payload, written by the gateway — storing them twice would be duplication, and the shared key makes it unnecessary.

3.4 · Decisions, and why

  • ①Trust the header because the gateway makes it trustworthy. The proxy strips client-sent copies of x-request-id before injecting its own, and direct calls to :8002 are rejected by INTERNAL_API_KEY. The retriever can adopt the header without validating provenance itself.
  • ②Adopt, don't mint. One line (api.py:68) turns two disconnected logs into a joinable pair. The uuid fallback keeps tests and ad-hoc curls working unchanged.
  • ③Capture retriever-side, in finally:, off the yield path. The audit considered a gateway tee of the response stream and rejected it: the streaming path has regressed to fake-streaming twice, and the retriever's finally: already holds the complete TurnResult for free. The daemon thread exists because finally: runs before the trailing done frame — a blocking POST there would delay the frame every client waits for. Bonus: the capture fires even when the client disconnects mid-stream, which is exactly the kind of turn an eval corpus wants.
  • ④Plain PostgREST over httpx, no SDK. Same shape as services/search/agent/reports.py — an existing in-repo pattern reused rather than a new dependency.
  • ⑤Telemetry semantics: log and swallow. A turn must never fail because the record write did. The trade: silent data loss if Supabase is down — visible only in service logs.
  • ⑥Empty SUPABASE_URL disables the write. The kill switch doubles as test isolation: tests/conftest.py blanks it, because the root .env's real URL would have made every endpoint test insert live rows.
  • ⑦Service-role-only RLS, identical to conversation_logs: RLS enabled with zero user policies, so no anon or authenticated client can read or write it.
  • ⑧Migration numbering is coordination. The file takes 18, so phase G's review-signal columns (which migration 17's notes pointed at 18) move to 19 — recorded in the migration header and the commit body, because the collision would otherwise surface months later.

3.5 · For a scalable system

  • Thread-per-turn has a ceiling. Every turn spawns one daemon thread and one HTTP POST. At current volume (~hundreds of turns/day) this is free; at hundreds of turns/minute it becomes unbounded concurrency against PostgREST. Upgrade path when it matters: a bounded in-process queue with one writer thread, batching inserts. The 15 s httpx timeout already bounds each hung post.
  • Daemon threads die with the process. A Fly deploy or crash mid-write loses that record. Acceptable for telemetry; do not later hang anything transactional off this path.
  • Growth is append-only and prunable. final_text plus three arrays per turn; eval_records_created_idx exists precisely so a retention job can prune by age cheaply. Decide retention before the table is big, not after.
  • No unique constraint on request_id — deliberately. The gateway mints a fresh id per request, so duplicates don't occur in the proxied path, and enforcing uniqueness would make a legitimate retry a hard failure in a path that must never fail.
  • Columns are loose (text, not enums) so classifier vocabulary can evolve without migrations. The eval harness, not the schema, is where strictness belongs.

3.6 · Security

  • The service-role key now lives in a second service. The retriever joins the gateway (and search) as a holder of the full-RLS-bypass key. Compromise of any one service is compromise of the whole database. Acceptable at this size; the eventual mitigation is a scoped Postgres role (insert-only on the telemetry tables) rather than the master key everywhere.
  • Header spoofing is closed at the boundary (decision ①): clients cannot choose their request_id, so they cannot write records that impersonate another turn — in the proxied path. Direct service calls are gated by INTERNAL_API_KEY.
  • The corpus is attacker-influenceable by construction. final_text derives from user-shaped conversations, and users know it. Anything that later reads this table — admin UIs (escape it), LLM judges (prompt-injection surface) — must treat every column as untrusted input.
  • RLS-on-no-policies means a leaked anon key still reads nothing. The only read path is the service role.
  • PII lives here now. Answers can echo user text and location. This table joins conversation_logs in any future data-deletion or retention obligation — see recommendations in §6.

Key takeaways — phase 0

  • The whole phase is: adopt one header, flatten one object that already existed, insert one row from a place that already ran. The design work was choosing that place.
  • The two invariants that shaped everything: the done frame is never delayed, and a turn never fails because telemetry did.
  • Capture lives where the data lives. The gateway logs what it has (the request); the retriever logs what it has (the answer); nobody buffers anybody else's stream.

4 · Phase 1 — the thumbs-down P1

4.1 · Goal

Attach the cheapest possible quality label to finished turns: a thumbs-down from the person who just read the answer, with an optional typed reason. No thumbs-up — the down is the informative event. This is the "cheap label" step of the corrected eval order, and it was scheduled early because it depends on nothing and compounds while the rest is built: roadmap §7's self-improvement loop has no signal without it.

Server-side, the route is native to the gateway — no proxying, no service hop — and does boundary validation before writing with the service role:

services/gateway/src/feedback.ts:19–44 — validate, then writeP1
app.post("/api/chat/feedback", async (request, reply) => {
  const requestId = body?.request_id;
  const reason = body?.reason ?? null;
  if (typeof requestId !== "string" || requestId.length === 0 || requestId.length > 128)
    return reply.code(400).send({ error: "request_id required" });          // ⓔ
  if (reason !== null && (typeof reason !== "string" || reason.length > 2000))
    return reply.code(400).send({ error: "reason must be a string of at most 2000 chars" });

  const response = await fetch(endpoint, {   // PostgREST, service role
    method: "POST", headers,
    body: JSON.stringify({
      request_id: requestId,
      user_id: request.user?.id ?? null,     // ⓕ from the verified JWT, never the body
      reason,
    }),
  });
  if (!response.ok) return reply.code(502).send({ error: "feedback not recorded" });
  return reply.code(204).send();
});

4.4 · Decisions, and why

  • ⓐCarry the key in the response header, not a frame. The retriever already set X-Request-ID on the streaming response (phase 0); the proxy passes response headers through, and the gateway's CORS config already listed it in exposedHeaders (server.ts:36) — so the browser can read it cross-origin with zero protocol changes. The typed SSE protocol stays untouched.
  • ⓑThe id doubles as the "finished" flag. streamChat only returns after the stream is consumed, so message.requestId being set means the turn completed — one field instead of a separate isStreaming flag, and the button can never target a half-finished answer.
  • ⓒPost on click, not on submit. Most users will never type a reason. If the signal waited for the reason box, an abandoned box would silently discard the down — the common case would lose the data. The click is the datum; the reason is a bonus.
  • ⓓNative gateway route, registered before the proxies. Feedback is a pure Postgres write with no retrieval logic, so it earns no service hop. Fastify's router prefers the static /api/chat/feedback over the /api/chat/* proxy wildcard, so it slots into the existing URL namespace without touching the proxy.
  • ⓔBoundary validation stays even though the endpoint is "just telemetry". Type and length checks (128 / 2000) bound every row an anonymous stranger can create.
  • ⓕAnonymous allowed, identity taken only from the verified JWT. Chat is anonymous by decision (D7); its feedback must be too, or the anonymous majority's signal is lost. user_id comes from request.user — never from the body — so it cannot be spoofed.
  • ⓖThe reason is a second row, not an update. Append-only keeps the gateway stateless (no row id round-trip, no PATCH path, no RLS update policy) and both timestamps survive. The cost is pushed to read time: analysis groups by request_id and coalesces.
  • ·No thumbs-up. Ups are noise (politeness, misclicks) that would dominate the table without informing anything. One button, one meaning.

4.5 · For a scalable system

  • Spam is bounded by the existing global rate limit (Redis-backed, per-identity, shared across replicas) — no new limiter was added, and none is needed until feedback abuse actually shows up.
  • Junk request_ids are accepted by design (any string ≤128). Validating existence against eval_records would add a read per click for no analytical gain — junk rows join to nothing and fall out of every query. Revisit only if the table fills with garbage.
  • Double-downs are prevented by UI state, not the database. The state machine hides the button after a click; a reload wipes the (stateless, client-carried) conversation entirely, button included. If feedback ever needs to survive reloads, dedup becomes the server's job — a unique index on (request_id, user_id) won't work for anonymous rows, so it would be a read-time distinct.
  • Volume is self-limiting — at most a few rows per human per turn. This table will stay small long after eval_records needs retention.

4.6 · Security

  • An anonymous, unauthenticated endpoint that writes with the service role is the sharpest edge here. It is safe because the route constructs the row itself from three validated values — the client cannot name columns, and user_id comes from the JWT. Any future column added to this insert must keep that property (no body spread into the PostgREST payload).
  • reason is hostile free text, stored raw. Correct at write time — but every future reader (admin dashboard, LLM error-analysis, judge prompts) must escape or fence it. A feedback box is a prompt-injection mailbox for anyone who suspects an LLM will read it.
  • Failure responses leak nothing: a PostgREST error is logged with its status but the client gets a flat 502.
  • Nothing is readable back. Same RLS posture as the other two tables; the SPA can write a down but no client can enumerate feedback.
  • Feedback links identity to opinion: a signed-in user's user_id plus free text is personal data. It inherits the same retention question as the other tables.

Key takeaways — phase 1

  • The entire feature is ~90 frontend lines, ~45 gateway lines, one table — because phase 0 had already put the join key in the browser's hands via a response header.
  • The two UX-shaped data decisions (post on click; reason as second row) both follow one rule: never let the optional part of an interaction destroy the mandatory part's data.
  • Asymmetric feedback (down only) is an eval decision, not a UX one: store only events that change what you'd do next.

5 · The join: one key, three tables

What the two phases actually built is a three-way join. Chat is stateless — the client resends the whole history each turn — which has a lucky consequence: the gateway's request-side log of a turn contains the entire conversation up to that point, not just the last message. One key therefore links complaint, conversation, and output:

Fig. 4 — The eval corpus is this join, not any single table.

example — the error-analysis query these phases were built for
-- every complaint, with the conversation that led to it and the answer it got
select f.created_at,
       max(f.reason)                          as reason,      -- coalesce the two-row model
       c.payload -> 'messages'                as conversation,
       e.final_text, e.query_type, e.cyphers, e.row_count, e.latency_ms, e.errors,
       c.duration_ms - e.latency_ms           as edge_overhead_ms  -- free metric from the join
from turn_feedback f
join eval_records       e using (request_id)
left join conversation_logs c on c.request_id = f.request_id
where f.rating = 'down'                       -- ups are labels, not complaints (migration 21)
group by f.request_id, f.created_at, c.payload, e.final_text, e.query_type,
         e.cyphers, e.row_count, e.latency_ms, e.errors, c.duration_ms
order by f.created_at desc;

Key takeaways

  • Each writer records only what it uniquely holds; the key does the assembly. No service buffers another's data, no capture pipeline exists.
  • Stateless chat turned out to be an eval asset: the request log is the full conversation snapshot at that turn.
  • Two latency figures for free: pipeline time (retriever) vs edge time (gateway) — their difference is proxy + queue overhead, measured per turn without any new instrumentation.

6.2 · Recommendations and observations

  1. Feedback reasons were stored twice — fixed on this branch. LOGGED_ROUTES in logging.ts matched /api/chat/feedback (the regex is ^\/api\/chat(\/|$)), so every feedback POST also landed in conversation_logs — under the feedback request's own fresh request.id, duplicating potentially personal free text into a second table. The route is now excluded from conversation logging, with a test pinning it.
  2. Retention — decided and scheduled on this branch. Migration 20260827000020_telemetry_retention.sql: two nightly pg_cron jobs prune conversation_logs and eval_records older than 90 days, except turns thumbed down (rating = 'down'; migration 21's ups do not pin) — down-labeled turns are the corpus and are kept indefinitely, as is turn_feedback itself. pg_cron so the schedule lives in the database and needs no running service. eval_records_created_idx makes the age scan cheap.
  3. The stale comment in logging.ts still says response-side capture "is Phase 6's eval-record work" — that work now exists, retriever-side. One-line docstring fix next time the file is touched.
  4. Thread-per-turn is marked as a known ceiling (§3.5) — worth a ponytail:-style comment in _write_eval_record naming the upgrade path (bounded queue + single writer) so the shortcut is tracked, not rediscovered under load.
  5. Build the reading habit before the harness. The corpus only pays for itself when someone reads it. The §5 query (or two or three variants: downs-with-reasons, error turns, slowest turns) belongs in a small docs/ or scripts/ snippet file so error analysis (phase 3) starts as a weekly five-minute habit, not a project.
  6. When judges arrive, the corpus is adversarial input. Both final_text and reason are user-influenceable and will eventually be interpolated into judge prompts. Fence them (delimiters + explicit "data, not instructions" framing) from the first judge prompt onwards — retrofitting this after a prompt-injection incident is the expensive order.
  7. Consider a scoped insert-only Postgres role for the telemetry writers once phase D/E raise the stakes: three services now hold the master service-role key, and none of them needs more than INSERT on two tables and SELECT on none.

Key takeaways — the plan

  • Phases 0+1 close the audit's two blockers: answers exist, and everything joins. The eval corpus now grows by itself with zero marginal effort.
  • The next cheap win (phase 2) is test plumbing, not new capability — 12 written cases are sitting in quarantine.
  • The expensive parts (rubrics, judges) stay parked until the corpus has taught what to grade — which is the whole point of the corrected order.
